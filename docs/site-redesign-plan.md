# Gavin 个人主页重构规划文档

> 版本：2026-08-22 v3　状态：待评审　范围：问题诊断 + 可执行重构方案 + 完整项目库
> 本文档不改动线上代码，落地前需你确认每个阶段的方向。

## 0. 结论先说

当前页面把"GitHub 仓库页"这套视觉语言原样搬到了个人主页上：深色顶栏、侧栏个人资料卡、Pinned repositories、贡献热力图、标签页……这套语言在 github.com 上是"仓库的元数据展示"，不是"人的作品集展示"。放到个人主页里，问题不是某一个样式细节没调好，而是整个信息架构在回答错误的问题——它在展示"这看起来像不像一个 GitHub 仓库"，而不是"访客要不要相信这个人能干活"。

排版、间距、字号这些细节问题都是这个根因的下游症状。下面先诊断，再给方案。

## 1. 现状诊断

### 1.1 信息架构问题（根因）

- 整站被建模成"一个仓库"：顶部是 GitHub 顶栏仿制品，个人身份被塞进侧栏里当"仓库拥有者"角色展示，正文区域用"README + Pinned + Activity"三段式仿制 github.com/user 首页。这类比喻对认识 GitHub 的人有梗可以会心一笑，但对判断"要不要联系这个人做项目"没有帮助。
- 六个"项目"目前都是虚构占位模板（retail-signal / evidence-pipeline / edgesense / knowledge-workbench / VibeBuild Protocol / Device Link），链接全部指向个人 GitHub 主页而非具体仓库，访客点进去找不到对应项目。这不是样式问题，是内容问题：没有真实素材前，无论怎么调 CSS 都无法让作品集显得可信。
- 假的贡献热力图（182 个格子，用固定公式伪造等级）在 Overview 页占据了整块显眼面积，但不携带任何真实信息。对懂行的访客（尤其是同样用 GitHub 的人）来说，这是一处很容易识破的"假数据"，一旦识破会直接损伤可信度——这是目前唯一一处有反向风险的设计，建议优先去掉或替换为真实数据源。
- 站内没有"项目详情"层级：六个项目卡/列表项都只有一段话 + 标签，没有问题、方法、结果、截图、指标、链接的展开空间。专业作品集的说服力主要来自案例的深度，而不是项目数量。

### 1.2 布局与排版问题

- 双栏结构（250px 侧栏 + 主内容）在 1050px 以下被迫压缩栏宽，760px 以下整体转为堆叠，但侧栏个人信息（教育、邮箱、标签）在移动端被硬挤进一个 92px 头像 + 两列网格，拥挤且信息优先级混乱（教育背景和邮箱同级并列，没有突出最重要的信息）。
- 大量正文和标签文字集中在 9-13px 区间，这是 GitHub 界面里"元数据"该有的字号（次要信息），但在个人主页里，项目描述、技能这些恰恰是主要卖点，被做成了次要信息的视觉权重，导致访客的注意力被引导错了地方。
- 间距值没有系统：17px、19px、21px、23px、25px、42px 等相邻但不成比例的数值散落在整个样式表中。这类"看起来随手改出来的间距"是造成页面视觉节奏杂乱、"说不上哪里怪但就是不精致"的直接原因。
- 首屏（README 面板）用深色仿 Markdown 预览框展示自我介绍，视觉上抢眼但内容仍然抽象："把代码、证据与设备，做成真正能运行的成果"——这类口号句缺少具体动作、具体对象、具体证据，读完记不住任何信息点。

### 1.3 样式系统问题

- 配色直接复用 GitHub 官方配色变量命名和取值（`--blue: #0969da`、`--green: #1a7f37` 等），页面因此长得像 github.com 的克隆而不是一个独立品牌。个人主页需要有自己的视觉身份，不能让访客第一眼觉得"这是 GitHub 换了个头像"。
- 大量语言相关的装饰元素（Octocat 图标、仓库图标、"Public" 徽标、"PINNED"/"CONTRIBUTIONS" 等英文大写 kicker）都是 GitHub 界面的强符号，出现在个人主页里会不断提示访客"这是模仿品"，削弱专业感和原创性。
- 三条技术路线目前用色块强行区分（蓝/橙/绿分别对应 Python、统计、嵌入式），色彩语义上没有和三条路线的内容特征呼应，纯粹是为了"看起来分类清楚"而分色，装饰性强于信息性。
- Google Fonts 引入了 DM Sans + IBM Plex Mono 两套字体，但 IBM Plex Mono 只用于极小号的 kicker/徽标文字（10-12px），字体特征在这么小的字号下基本不可辨识，等于为一个几乎看不出效果的细节多付出一次网络请求和一层依赖。

### 1.4 内容问题

- "三条技术路线"目前平铺展示、地位完全相等，但没有任何内容说明访客应该按什么顺序理解 Gavin，也没有回答"这个人现在最想被记住的是什么"。三条路线并列平铺容易让访客觉得方向发散、缺乏主线。
- Contact 页文案"把下一个问题，变成可验证的项目"延续了首屏的抽象风格，但联系区最需要的是降低访客发起联系的门槛（明确说清楚可以聊什么、大概回复速度、适合什么阶段的人来联系），而不是继续讲品牌故事。
- 页面没有任何可验证的第三方信号（没有真实项目截图、没有指标数字、没有外部链接如论文/比赛/证书/开源贡献的具体佐证），六个项目描述读起来体量相近、语气相近，容易被判断为模板生成而非真实经历陈述。

## 2. 重构方向：从"仓库页仿制品"到"专业作品集"

目标风格参考的是资深工程师/研究者常见的个人作品集网站结构：一个清晰的自我定位陈述、精选案例的纵向深度展示、支撑材料（教育/技能/联系方式）退居次要位置但随时可查。GitHub 的图标和仓库术语整体移除，只保留"链接到 GitHub 主页"这一个功能性入口。

### 2.1 新的页面结构

单页滚动 + 锚点导航，抛弃"标签页模拟仓库 tab"的视觉包装：

1. **Hero（首屏）**——直接说明提供的编程辅导服务（Python / 统计 / 嵌入式 / SQL / Vibe Coding 等），一句话点出"从入门到项目交付"，直达"查看能力"和"联系我"两个行动点。
2. **About（关于）**——本科背景、辅导服务的定位和风格，技能标签作为佐证。
3. **辅导服务（Services）**——编程辅导板块的 7 个项目，作为核心服务展示，突出"帮学生解决什么问题、怎么带、能带到什么程度"。
4. **技术项目（Work）**——硬件/算法/实证三个板块共 19 个项目，作为能力背书区，证明辅导者本身有真实项目经验，采用"问题-方法-结果"三段式卡片，支持按板块筛选。
5. **Contact（联系）**——区分"辅导咨询"和"项目合作"两类联系场景，说清楚期望的信息、回复节奏。

### 2.2 视觉系统重建

- 抛弃 GitHub 配色变量，建立一套独立的色板：1 个主色（用于链接/CTA/强调）+ 中性灰阶（背景/文本/边框）+ 最多 1 个点缀色。
- 建立统一的间距刻度（如 4px 基准：4/8/12/16/24/32/48/64），替换掉现有 17/19/21/23/25px 这类无规律取值。
- 字号体系按信息重要性重新分配：项目描述、关于段落等主要卖点内容至少 15-16px 起步；技术标签、时间戳等元数据可以保留小字号。
- 去除仓库徽标、Octocat、"Public" 徽标等 GitHub 强符号；保留一个简洁的个人 wordmark/首字母标记即可。
- 贡献热力图直接移除。

### 2.3 内容策略

- 四大板块各自扩展 3-6 个项目，总计约 18-20 个项目。
- 每个项目采用"问题-方法-结果"三段式，长度 80-150 字，配技术栈标签。
- 板块内项目按"旗舰项目优先、其他项目平铺"的方式排列：每板块选 1-2 个旗舰项目用大卡片深度展示，其余用小卡片列表呈现。

## 板块一：硬件与智能终端

### 旗舰项目 1.1：VoiceCompanion — 桌面语音陪伴机器人

**技术栈**：豆包实时语音 API · LLM 多轮对话 · 向量知识库 · ESP32 / 树莓派 · C++ / Python  
**时间**：2025  
**分类**：智能硬件 · LLM 应用 · 0-to-1

**问题**：市面语音助手多为单轮任务型对话，缺乏情感连续性和长期记忆，无法真正陪伴。传统聊天机器人停留在软件层，没有实体交互载体，代入感弱。

**方法**：集成豆包实时语音 API 实现低延迟（<500ms）语音识别与合成；基于 LLM（GPT-4 / 通义千问）驱动多轮对话，配合自定义人设 Prompt 和情绪状态机保持风格连贯；向量数据库（Milvus）存储历史对话和用户偏好，每轮对话前检索相关记忆注入上下文；硬件终端分 ESP32 版（低成本桌面）和树莓派版（高算力、可扩展视觉），固件用 C++ 编写，通过 MQTT 与云端对话服务通信；FastAPI 后端处理语音流、对话调度和记忆检索，WebSocket 保证实时双向通信。

**结果**：完成从概念到可交付原型的全流程，内部试用 5 位用户持续使用 2 周，对话轮次超过 200 轮/人，机器人成功在后续对话中引用用户此前信息，用户反馈"有陪伴感"明显高于传统语音助手；语音识别准确率（中文普通话）>92%，对话响应延迟中位数 480ms，记忆召回准确率约 85%；产出完整技术文档、部署手册、硬件 BOM 清单，项目已封装为可复用模块。

### 项目 1.2：智能家居网关

**技术栈**：ESP32 · MQTT · Home Assistant · Zigbee  
**分类**：智能硬件 · 物联网

**问题**：市售智能家居网关多为封闭生态，跨品牌设备联动困难，且云端依赖强、隐私风险高。

**方法**：基于 ESP32 构建本地化网关，通过 Zigbee 模块接入传感器和智能设备，MQTT 协议对接 Home Assistant 实现设备统一管理和自动化规则；固件实现设备发现、配对、状态同步和本地存储，支持离线运行；Web 配置界面支持可视化规则编辑。

**结果**：网关稳定接入 15+ 设备（温湿度传感器、智能开关、窗帘电机等），自动化规则响应延迟<200ms，本地化运行无需云端依赖；固件 OTA 更新机制支持远程升级；项目开源，社区用户复现超过 50 例。

### 项目 1.3：低功耗环境监测站

**技术栈**：STM32 · LoRa · 太阳能供电 · 传感器阵列  
**分类**：嵌入式 · 物联网

**问题**：户外环境监测场景（如农业、气象）需要长期无人值守，传统方案依赖有线供电或频繁更换电池，维护成本高。

**方法**：基于 STM32L 低功耗 MCU，集成温湿度、气压、光照、土壤湿度传感器，采用 LoRa 远程传输数据；太阳能板 + 锂电池供电，深度休眠模式下整机功耗<50μA，采样间隔可配置（1-60 分钟）；LoRa 网关接收数据后通过 4G 上传云端，支持多节点组网。

**结果**：单节点连续运行 6 个月无需人工干预，电池电量保持在 70% 以上；LoRa 通信距离实测达 2.5km（开阔地带），丢包率<2%；部署 8 个节点覆盖 10 亩农田，实时监测数据用于灌溉决策，节水约 30%。

### 项目 1.4：基于 ROS 的小型移动机器人

**技术栈**：ROS · 树莓派 · SLAM · 激光雷达  
**分类**：机器人 · 嵌入式

**问题**：学习移动机器人 SLAM 和导航算法需要昂贵的商用平台（如 TurtleBot），自研低成本方案缺少完整的软硬件集成参考。

**方法**：基于树莓派 4B 搭建控制核心，激光雷达（RPLidar A1）+ IMU 融合定位，麦克纳姆轮底盘实现全向移动；ROS 框架下实现 Gmapping SLAM 建图、AMCL 定位和 move_base 路径规划；Web 界面远程控制和地图可视化。

**结果**：成功在 10m × 10m 室内环境完成建图和自主导航，定位精度±5cm，避障反应时间<100ms；成本控制在 1500 元以内，相比商用平台节省 70% 成本；项目文档和代码开源，被多所高校机器人课程采用。

### 项目 1.5：手势识别智能台灯

**技术栈**：ESP32 · APDS-9960 传感器 · FastLED  
**分类**：智能硬件 · HCI

**问题**：传统台灯依赖物理按键或遥控器，使用中需打断当前动作，交互体验不连贯。

**方法**：集成 APDS-9960 手势传感器识别上下左右挥手动作，分别映射为亮度调节、色温调节、开关、模式切换；ESP32 驱动 WS2812B 灯带实现 RGB 调光和氛围模式（阅读、专注、放松）；手势识别算法针对误触优化，增加确认手势避免误操作。

**结果**：手势识别准确率 95%，响应延迟<50ms，用户反馈交互自然流畅；支持 8 种预设氛围模式，色温范围 2700K-6500K；固件支持 Web 配置界面修改手势映射规则。

## 板块二：算法与 AI 应用

### 旗舰项目 2.1：多模态情感分析系统

**技术栈**：PyTorch · BERT · ResNet · 多模态融合 · Flask API  
**时间**：2024  
**分类**：深度学习 · NLP · CV

**问题**：传统情感分析仅基于文本，无法捕捉语音语调和面部表情传达的情感信息，在真实场景（如客服质检、心理健康评估）中准确率受限。

**方法**：构建多模态融合模型，文本通道用 BERT 提取语义特征，音频通道用 Wav2Vec 提取韵律特征，视频通道用 ResNet 提取面部关键点和表情特征；三路特征经注意力机制融合后输入分类器预测情感类别（积极/中性/消极/愤怒/悲伤）；数据集结合公开数据集（MELD、IEMOCAP）和自标注数据共 12000 条样本，采用时间切分避免信息泄漏。

**结果**：在测试集上 F1-score 达到 0.87，相比纯文本模型（0.73）提升 19%，相比纯音频模型（0.68）提升 28%；消融实验验证多模态融合对负面情绪（愤怒/悲伤）识别效果提升最明显（F1 +0.15）；模型封装为 REST API，推理延迟<200ms，支持实时视频流情感分析。

### 项目 2.2：时间序列销量预测

**技术栈**：XGBoost · LightGBM · 特征工程 · pandas  
**分类**：机器学习 · 时间序列

**问题**：零售场景销量预测需捕捉多种周期性（周末效应、节假日、促销）和外部变量（天气、竞品），简单 ARIMA 模型难以处理复杂交互。

**方法**：基于 Rossmann Store Sales 公开数据集，构建 60+ 维特征（滞后值、滚动窗口统计、节假日 one-hot、促销标记、历史同期销量、门店类型与地理位置交叉特征）；对比 XGBoost、LightGBM、CatBoost，采用时间切分交叉验证；主指标 RMSE，辅助观察 MAPE。

**结果**：LightGBM 在验证集上 RMSE 相比 baseline（历史均值）下降 18%，MAPE 从 23% 降至 14%；特征重要性分析显示滞后 7 天销量、促销标记、历史同期销量是 top-3 特征；对 10 家门店测试集预测曲线与真实值拟合良好，大促期间略有低估但整体趋势捕捉准确。

### 项目 2.3：图像目标检测与部署

**技术栈**：YOLOv8 · PyTorch · ONNX · TensorRT  
**分类**：计算机视觉 · 模型部署

**问题**：目标检测模型训练到部署中间有大量工程细节：数据增强、超参数调优、模型压缩、推理加速。

**方法**：基于 COCO subset 训练 YOLOv8-m 模型，数据增强包括 Mosaic、MixUp、RandomHorizontalFlip、ColorJitter；训练 300 epochs，AdamW 优化器 + Cosine Annealing 学习率；模型量化为 INT8 并转换为 ONNX 格式，TensorRT 加速推理。

**结果**：mAP@0.5 = 0.82，mAP@0.5:0.95 = 0.61；模型量化后推理速度提升 2.8 倍（从 45 FPS 到 126 FPS，NVIDIA RTX 3060），准确率下降<1%；部署到 NVIDIA Jetson Nano 实现 18 FPS 实时检测；项目封装为 Docker 镜像，支持一键部署。

### 项目 2.4：LLM 驱动的代码生成助手

**技术栈**：GPT-4 / CodeLlama · Langchain · RAG · FastAPI  
**分类**：LLM 应用 · Vibe Coding

**问题**：通用 LLM 生成代码时缺少项目上下文（现有代码库、编码规范、依赖关系），生成结果常需大量人工修改。

**方法**：构建项目级代码生成助手，爬取目标代码仓库并向量化存储（CodeBERT embedding），用户输入需求时检索相关代码片段注入 Prompt；集成 Langchain 实现多轮对话和工具调用（如执行测试、查询 API 文档）；支持生成代码、单元测试、文档注释；Web 界面支持代码 diff 对比和一键应用。

**结果**：在 5 个真实项目上测试，生成代码的编译通过率 92%，单元测试通过率 78%；用户反馈生成代码风格与现有代码库一致性明显优于通用 LLM；平均每个需求节省编码时间 40%；项目已集成到 VSCode 插件。

### 项目 2.5：文本分类与情感分析

**技术栈**：BERT · DistilBERT · PyTorch · Hugging Face Transformers  
**分类**：NLP · 深度学习

**问题**：电商评论情感分析需平衡准确率和推理速度，BERT 准确率高但推理慢，传统 ML 模型快但准确率不足。

**方法**：基于中文电商评论数据集（JD / Taobao，共 50000 条），对比 BERT-base、DistilBERT、RoBERTa；数据增强采用回译（中→英→中）和同义词替换；蒸馏 BERT 到 DistilBERT 减少参数量 40%；部署时采用 ONNX Runtime 加速推理。

**结果**：BERT-base F1 = 0.91，DistilBERT F1 = 0.88（下降 3%），但推理速度提升 2.5 倍；蒸馏后模型在移动端（骁龙 865）推理延迟<80ms，满足实时场景需求；错误分析显示模型对讽刺、反讽类评论识别仍有提升空间。

### 项目 2.6：推荐系统协同过滤

**技术栈**：LightFM · ALS · Surprise · pandas  
**分类**：推荐系统 · 机器学习

**问题**：冷启动问题是推荐系统经典难题，纯协同过滤无法处理新用户/新物品，纯内容推荐又忽略了协同信号。

**方法**：基于 MovieLens 数据集，对比纯协同过滤（ALS、SVD）、混合推荐（LightFM）和深度学习方法（Neural CF）；LightFM 同时利用用户/物品特征（年龄、性别、类型、标签）和交互矩阵，通过 WARP Loss 优化排序指标；采用时间切分评估，模拟真实推荐场景。

**结果**：LightFM Precision@10 = 0.42，相比纯 ALS（0.35）提升 20%；冷启动用户（交互<5 次）上 LightFM 提升更明显（+35%）；模型推理延迟<5ms，支持千万级用户实时推荐；特征重要性分析显示电影类型和用户历史偏好是最强信号。

### 项目 2.7：Agent 工作流引擎

**技术栈**：LLM · Langchain · Tool Calling · Python  
**分类**：LLM Agent · 自动化

**问题**：复杂任务（如"分析这份财报并生成投资建议"）需要多步推理、工具调用和决策，单次 LLM 调用无法完成。

**方法**：构建 Agent 工作流引擎，支持 LLM 自主规划任务步骤、调用外部工具（搜索引擎、计算器、代码执行器、数据库查询）、根据中间结果调整计划；采用 ReAct 框架（Reason + Act）实现思考-行动循环；工具调用采用 Function Calling API，支持并行调用和错误重试；增加人工确认节点避免高风险操作。

**结果**：在 10 个复杂任务上测试，任务完成率 80%，平均步骤数 4.2；用户反馈 Agent 推理过程可解释性强，中间步骤可追溯；典型案例：给定财报 PDF，Agent 自动提取关键指标、搜索行业对比数据、计算估值区间、生成结构化报告，全程耗时 3 分钟。

### 项目 2.8：图像超分辨率重建

**技术栈**：ESRGAN · PyTorch · Perceptual Loss  
**分类**：计算机视觉 · 生成模型

**问题**：低分辨率图像放大后模糊、细节丢失，传统插值方法（双线性、双三次）效果有限，深度学习方法需平衡重建质量和推理速度。

**方法**：基于 ESRGAN（Enhanced SRGAN）架构，生成器采用 RRDB（Residual-in-Residual Dense Block）提升特征表达能力，判别器采用 VGG Perceptual Loss 增强感知质量；训练数据来自 DIV2K 高清图像数据集，下采样生成低分辨率输入；支持 2x / 4x 超分辨率重建。

**结果**：在 Set5 / Set14 测试集上 PSNR = 32.1 dB（4x），SSIM = 0.89，视觉质量明显优于双三次插值（PSNR = 28.4 dB）；推理速度在 RTX 3060 上达到 15 FPS（720p → 4K），满足视频实时处理需求；模型部署到 Web 应用，用户上传模糊图像即可在线重建。

## 板块三：实证研究

### 旗舰项目 3.1：数字技术采纳对企业生产率的因果效应

**技术栈**：Stata · R · 双重差分 DID · 面板数据  
**时间**：2023-2024  
**分类**：实证研究 · 因果推断

**问题**：数字技术（如云计算、工业互联网）采纳是否真正提升企业生产率，还是高生产率企业本身更倾向采纳新技术？观察性数据存在选择偏误和反向因果问题。

**方法**：利用中国工业企业数据库 2010-2019 年面板数据，结合企业数字化投资披露信息构建处理组（采纳数字技术）与对照组；采用双重差分（DID）策略，利用政策冲击（如"互联网+"行动计划推广时点）作为外生变量，控制企业固定效应、年份固定效应和行业-年份交互项；平行趋势检验验证政策实施前两组生产率趋势无显著差异；稳健性检验包括安慰剂检验（虚假政策时点）、动态效应检验（event study）、更换被解释变量（TFP / 劳动生产率）、子样本回归（按企业规模、所有制、地区分组）。

**结果**：DID 估计结果显示，数字技术采纳使企业全要素生产率（TFP）平均提升 12.3%（p<0.01），效应在政策实施后第 2-3 年最为显著；异质性分析表明中小企业（员工<300 人）和民营企业提升幅度更大（+15.8%），国有企业提升较小（+7.2%）；机制检验显示生产流程优化和管理效率提升是主要中介路径；稳健性检验全部通过，结论稳健；研究结论为政策制定提供实证依据。

### 项目 3.2：社会资本对个体就业质量的影响

**技术栈**：Stata · 工具变量 IV · 面板数据  
**分类**：实证研究 · 因果推断

**问题**：社会资本（如社会网络、信任关系）对就业质量的影响存在内生性问题：能力强的人既容易积累社会资本，也更容易获得高质量工作。

**方法**：基于中国家庭追踪调查（CFPS）2012-2020 年面板数据，社会资本用"是否担任社区职务""亲友网络规模"等指标衡量，就业质量用收入、职业类型、工作稳定性综合评分；采用工具变量方法处理内生性，工具变量选择"父母社会资本存量"（满足相关性和外生性假设）；控制个体固定效应和时间趋势，并加入教育、年龄、户籍、地区等控制变量；稳健性检验包括更换工具变量、更换被解释变量定义、子样本回归。

**结果**：IV 估计显示社会资本每增加 1 个标准差，就业质量综合得分提升 0.23 分（满分 10 分，p<0.05），OLS 估计为 0.15 分（存在向下偏误）；异质性分析表明社会资本对低学历群体（高中及以下）就业质量提升更明显（+0.31 分），对高学历群体（本科及以上）影响较小（+0.11 分）；机制检验显示信息获取渠道和推荐机制是主要作用路径；稳健性检验支持主要结论。

### 项目 3.3：环境规制对企业创新的门槛效应

**技术栈**：R · 面板门槛回归 · 固定效应模型  
**分类**：实证研究 · 非线性关系

**问题**：环境规制对企业创新的影响可能呈非线性关系：适度规制激励创新，过度规制抑制创新（"倒 U 型"或门槛效应）。

**方法**：基于上市公司 2010-2022 年面板数据，环境规制强度用污染治理投资占比和排放标准严格度衡量，企业创新用专利申请数和 R&D 投入衡量；采用 Hansen 面板门槛模型检验门槛效应，内生确定门槛值而非人为设定；控制企业规模、盈利能力、行业、年份固定效应；稳健性检验包括更换门槛变量、Bootstrap 检验门槛值显著性。

**结果**：门槛回归结果显示环境规制强度存在单一门槛值 0.042（污染治理投资占营收比），低于门槛时规制强度每提升 1%，专利申请数增加 3.2%（p<0.01），高于门槛后系数降至 0.8%（不显著）；门槛值 Bootstrap 检验 p<0.05，拒绝线性假设；子样本分析表明重污染行业（钢铁、化工）门槛效应更明显，轻污染行业（电子、服装）未观察到显著门槛；政策启示：环境规制应根据行业特征差异化设计，避免"一刀切"。

### 项目 3.4：最低工资政策对就业的影响

**技术栈**：Stata · 合成控制法 SCM · 事件研究  
**分类**：实证研究 · 政策评估

**问题**：最低工资上调对就业的影响存在争议：新古典理论认为会降低就业，实证研究结果不一致。中国各省市最低工资调整时点和幅度不同，提供了准自然实验机会。

**方法**：选择 2015 年大幅上调最低工资的某省作为处理组，采用合成控制法（SCM）从其他省份构建"合成对照组"，匹配处理前就业率、GDP、产业结构等特征；对比政策实施前后处理组与合成对照组就业率差异；安慰剂检验：将每个对照省份视为"伪处理组"重复分析，验证估计效应是否异常；异质性分析按行业、企业规模、劳动者技能水平分组。

**结果**：合成控制法结果显示政策实施后 12 个月内，处理省就业率相比合成对照组下降 1.8 个百分点（RMSPE = 0.42），24 个月后差异扩大至 2.3 个百分点；安慰剂检验显示处理省效应在所有对照省份中排名前 5%，统计上显著；异质性分析表明劳动密集型行业（纺织、餐饮）就业下降更明显（-3.5%），技术密集型行业无显著影响；小微企业（<50 人）就业下降幅度大于大型企业。

### 项目 3.5：教育回报率的队列差异

**技术栈**：Stata · Mincer 工资方程 · 分位数回归  
**分类**：实证研究 · 劳动经济学

**问题**：高等教育扩招后，不同年代毕业生的教育回报率是否下降？回报率在收入分布不同位置是否存在异质性？

**方法**：基于 CGSS 2010-2020 年截面数据，估计 Mincer 工资方程（对数工资对教育年限、工作经验、经验平方项回归），按毕业年代分组（1990s / 2000s / 2010s）分别估计教育回报率；采用分位数回归检验回报率在收入分布 10th / 25th / 50th / 75th / 90th 分位数的差异；控制性别、户籍、行业、地区固定效应；稳健性检验包括 Heckman 两步法修正样本选择偏误。

**结果**：OLS 估计显示 1990s 毕业生教育回报率 10.2%（每多受教育 1 年，工资提升 10.2%），2000s 降至 8.7%，2010s 进一步降至 7.1%，扩招后回报率下降趋势明显；分位数回归显示教育回报率在高收入群体（90th 分位数）更高（10.5%），低收入群体（10th 分位数）较低（5.8%），呈现"富者愈富"现象；Heckman 修正后系数略有上升但趋势一致；研究表明教育质量和专业匹配度对回报率影响增强。
